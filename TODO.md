- [ ] **Resolving a reference: one lookup in the registry (owner, 2026-11-05; found on `refactor/plan-holds-no-data` at `589fbfd7`, probably for the namespaces refactor).** Recheck this list on whatever branch does it: the code below may have moved or changed there.
  Owner's rule: a reference (a value or a type, as the user wrote it) is what later names a key, and the key is in the registry. Resolving is one call, reference → key, with nothing in between and nothing taken from the resolved plan (`resolved[:key]`). A reference that already holds its key (a `Symbol` key, a keyed handle, a fixed namespace such as function calls) is a no-op. Lookups pick the static or the dynamic path by the reference's type (`isstaticallyfindable`) and never use `try`/`catch` (`get(reg, obj, default)` done in `589fbfd7`). For resolving at construction, an internal `@nospecialize` path (`getkey_nospecialize(reg, ref)`) should be faster than the generated static lookup; it matches the reference against the entries (no hand-written `match_by` comparison). Get every call site onto one function first, so its body can be swapped. `ctx[obj]` (`getkey(reg[obj])`) is fine as it is.
  Where references are resolved otherwise today:
  1. `InitArgs`/`Override`/`Interactive` targets, `resolve(reg, ::InputInterface)` (`src/InputInterface/Resolving.jl`): object → `static_findkey`; matcher → `get_by_matcher` (a recursive walk over all algorithms) then `getkey`; `Symbol` → `haskey` check.
  2. `Only` targets, `resolve(reg, ::Only)` (same file): a throwaway `InitArgs(target)` per target, its key read back with `get_target`. (Tried 2026-11-05 to replace it with a direct lookup: with the precompile workload's `init(..., Only(:counter))` (`src/Precompile.jl`) the package image then failed to load on Julia 1.13.1 (`UndefRefError` while Julia checks the cache), the known failure from a lookup by name in the workload; reverted.)
  3. `Route`/`Share`/`Redirect` endpoints, `resolve_scref` (`src/SubContextRefs.jl`): a chain of fallbacks: `fixed_namespace`, else the key a keyed handle holds, else `getkey(reg, object)`, else `matcher_sckey` (a type: `findall(T, reg)` and the first match; another matcher: a loop over all algorithms comparing `match_by`).
  4. `Var(A, :x)` selectors (`Until`, `view`), `_var_subcontext` (`src/Context/Vars.jl`): straight to `matcher_sckey`, when the `Var` is read (not at resolve; whether the compiler folds it is unchecked).
  5. `ContextExchange` targets (inactive), `_resolve_exchange_entity` (`src/Interactive/ContextExchange.jl`): a type → `findall`, exactly one match required; other matchers → `resolve_scref`.
  6. `getkey(la, obj)` (`src/LoopAlgorithms/Accessors.jl`) → `getkey(reg, obj)` through the plan.
  7. `view(scv, instance)` (`src/Context/View/ContextView.jl`): `static_get` then `getkey`, to check the subcontext.
  8. Old threaded views (`src/Threaded/OldProcessContextView.jl`): `static_get` on the type or the instance; left for the threaded fix.
  The registry has overlapping lookups to fold into the one call: `static_findkey`, `getkey(reg, obj)`, `reg[obj]`, `get(reg, obj)`, `static_get`, `static_get_match`, `dynamic_get`, `get_by_matcher`, `findall(T, reg)`, `findfirst_match`.

## Modes of operation (agreed 2026-11-03)
- [ ] **Three modes of operation, each with one clear owner of the plan and its contexts.** Write each down (who owns the plan and the contexts, what the user calls, what comes back), make every process type fit exactly one, and give them a user docs page.
  1. **Direct runs (plan and context directly).** The user gets a context from the plan, or from the first run of a plan with no process around it, and runs the plan on it from their own code. Init on a plan returns a context that the user owns and moves around; it is not put into the plan. This mode is for embedding the package in other code: it gives a clear entry point to the data. Also in this mode: tools to split a plan into parts, so the user can build their own code around parts of a plan; and resolving several plans together without merging them, with one context for all of them (the multi-plan resolve, `src/LoopAlgorithms/Resolving/Resolving.jl`). Related on `refactor/plan-compiles` (TODO.md, "API readability"): "Running without a process" and "`run(plan)` is untyped at its entry". How exactly a run returns the changed context is decided later.
  2. **Process.** Once a plan is in a process, the process manages the plan and its contexts: the state context (the user's handle, with the registry), and while paused the run's runtime context. The process is the entry point for running, pausing, resuming and closing; the user reads the context only when they want it (`getcontext(p)` returns only the handle, never the runtime context). Most direct users of the package work in this mode. Check every process type against it: `Process`, `InlineProcess`, `TimedProcess` (`LoopRunProcess` removed on `refactor/contexts-processes-pausing`: the loop runs on a `ProcessSession`) (rewritten on the `Process` design 2026-11-04).   3. **Manager.** The manager keeps track of processes (its workers) and runs jobs on them over threads; the user goes through the manager, not the workers.
